## 1. 구조체 (`STRUCT`)와 메모리 정렬 (`ALIGN`)

### ① 왜 `ALIGN`(정렬)을 해야 할까? ("2번 접근"의 원리)
* 32비트 CPU(x86)는 메모리를 1바이트씩 읽지 않고 **4바이트(32비트) 덩어리 단위(0번지, 4번지, 8번지...)**로 퍼 올립니다.
* 변수 주소가 자료형 크기의 배수(짝수 번지, 4의 배수 번지 등)에 맞지 않으면, 데이터가 메모리 경계에 걸쳐 CPU가 **메모리에 2번 접근**해 데이터를 합쳐야 하므로 실행 속도가 느려집니다.
* 이를 방지하기 위해 멤버 사이에 빈칸(패딩 바이트)을 채워 주소를 맞추는 지시어가 **`ALIGN`**입니다.

### ② 슬라이드 `Employee` 구조체 크기 계산법 (총 60바이트)
시험에서 가장 자주 나오는 **"패딩 바이트 수 및 전체 구조체 크기(`SIZEOF`) 계산"** 예제입니다.

```assembly
Employee STRUCT
    IdNum         BYTE "000000000"    ; 1. 0~8번지 사용 (9바이트)
    LastName      BYTE 30 DUP(0)      ; 2. 9~38번지 사용 (30바이트) -> 현재 누적 39바이트(홀수!)
    ALIGN         WORD                ; 3. WORD(2바이트)를 위해 짝수 번지(40) 맞춤 -> [1바이트 패딩 추가]
    Years         WORD 0              ; 4. 40~41번지 사용 (2바이트) -> 현재 누적 42바이트
    ALIGN         DWORD               ; 5. DWORD(4바이트)를 위해 4의 배수(44) 맞춤 -> [2바이트 패딩 추가]
    SalaryHistory DWORD 0,0,0,0       ; 6. 44~59번지 사용 (4바이트 × 4개 = 16바이트)
Employee ENDS                         ; -> 총 합계: 9 + 30 + 1 + 2 + 2 + 16 = 60바이트!
```

### ③ 자료형별 정렬 기준 (`Table 10-1`)

| 자료형 (`Member Type`) | 정렬 기준 (`Alignment`) | 쉬운 의미 |
| :--- | :--- | :--- |
| **`BYTE`, `SBYTE`** | 8-bit (1바이트) 경계 | 어디든 상관없음 (모든 주소가 1의 배수) |
| **`WORD`, `SWORD`** | 16-bit (2바이트) 경계 | **2의 배수** 주소(짝수 번지)에서 시작 |
| **`DWORD`, `SDWORD`, `REAL4`** | 32-bit (4바이트) 경계 | **4의 배수** 주소에서 시작 |
| **`QWORD`, `REAL8`** | 64-bit (8바이트) 경계 | **8의 배수** 주소에서 시작 |
| **`structure` (구조체)** | 가장 큰 멤버의 정렬 기준 | 구조체 내 가장 큰 자료형의 배수로 정렬 |
| **`union` (유니온)** | 첫 번째 멤버의 정렬 기준 | 첫 번째 선언된 멤버 크기의 배수로 정렬 |

## 2. 구조체의 메모리 주소 참조 (`OFFSET` + `PTR`)

구조체 변수의 시작 주소를 레지스터(`ESI` 등)에 담아 간접 주소 지정(포인터처럼)으로 멤버에 접근할 때는 **반드시 `PTR` 연산자**를 사용해 해당 주소를 어떤 구조체로 해석할지 알려줘야 합니다.

```assembly
.data
worker Employee <>

.code
mov esi, OFFSET worker              ; 1단계: worker 구조체의 시작 메모리 주소를 ESI에 저장
mov ax, (Employee PTR [esi]).Years  ; 2단계: ESI 주소를 Employee 구조체로 해석해 .Years 멤버 참조
```
* **`OFFSET` 연산자**: 변수나 구조체 필드가 메모리 몇 번지에서 시작하는지 **시작 주소**를 가져옵니다.
* **`Employee PTR [esi]`**: 레지스터 `ESI` 안에는 단순 주소 숫자만 들어있으므로, CPU에게 *"이 주소를 `Employee` 구조체 틀로 읽어라"*라고 지정하는 역할을 합니다.

## 3. 공용체 (`UNION`)의 특징
* 구조체(`STRUCT`)는 멤버마다 각자의 메모리 공간을 따로 차지하지만, **유니온(`UNION`)은 모든 멤버가 동일한 메모리 시작 주소(오프셋 0)를 공유**합니다.
* 전체 크기는 **가장 큰 멤버의 크기**와 같습니다.
* 초기값을 여러 멤버에 다르게 적더라도 **첫 번째 멤버의 초기값만 적용**되고 나머지는 무시됩니다.

```assembly
Integer UNION
    D DWORD 1       ; 4바이트 (가장 크므로 전체 크기는 4바이트, 초기값 1 적용)
    W WORD  5       ; 무시됨
    B BYTE  8       ; 무시됨
Integer ENDS
```

## 4. 매크로 (`MACRO`)와 필수 매개변수 (`:REQ`)

* **매크로(Macro)**: 호출한 위치에 어셈블리 코드가 그대로 복사되어 삽입(인라인 확장)되는 코드 블록입니다. (`MACRO` ~ `ENDM`)
* **`:REQ` (Required Parameter)**:
  * 자바(Java)에서 메서드를 선언할 때 `void printChar(char c)`처럼 매개변수를 적어두면 호출 시 반드시 인자값을 넘겨야 컴파일이 되는 것과 같은 원리입니다.
  * 어셈블리 매크로는 기본적으로 인자 생략이 가능하므로, **인자값을 빼먹지 않고 반드시 전달받도록 강제**하려면 매개변수 뒤에 **`:REQ`**를 붙입니다.

```assembly
mPutchar MACRO char:REQ     ; char 인자값이 비어있으면 어셈블 시 에러 발생!
    push eax
    mov  al, char
    call WriteChar
    pop  eax
ENDM
```

## 5. Irvine32 기본 입출력 4대 공식 & 스택 대피 원리

### ① 한눈에 보는 입출력 4대 공식

| 목적 | 사용하는 레지스터 | 호출하는 함수 | 동작 원리 |
| :--- | :--- | :--- | :--- |
| **글자 출력** | **`EDX`**에 문자열 시작 주소(`OFFSET`) 넣기 | `call WriteString` | `EDX` 번지부터 끝(`0`)이 나올 때까지 화면에 출력 |
| **숫자 입력** | 입력된 값이 자동으로 **`EAX`**에 도착 | `call ReadInt` | 키보드로 입력한 정수가 `EAX`에 저장됨 |
| **숫자 출력** | 출력할 숫자를 **`EAX`**에 넣기 | `call WriteInt` | `EAX`에 들어있는 숫자를 화면에 출력 |
| **줄바꿈** | 없음 | `call Crlf` | 화면에 엔터키(`\n`) 한 번 출력 |

### ② 출력 전 `PUSH` / `POP`으로 레지스터를 보호하는 이유
* `WriteString` 같은 라이브러리 함수를 호출하면, 내부 실행 과정에서 **`EAX` 등의 레지스터 값이 덮어씌워져 망가질 수 있습니다.**
* 따라서 중요한 계산 결과(`EAX`)를 화면에 출력하기 전에:
  1. **`push eax`**: 계산 결과를 안전한 창고(스택)에 잠시 숨겨둠
  2. **`mov edx, OFFSET msg` + `call WriteString`**: 안내 문구 출력
  3. **`pop eax`**: 숨겨뒀던 계산 결과를 다시 `EAX`로 복원
  4. **`call WriteInt`**: 복원된 숫자 출력
